# 하네스 전체 흐름

Oct 25, 2026 · @백찬

## 한 줄로

사람이 뿌리 명세를 세우면, AI가 필요한 만큼만 트리를 쪼개고 잎 티켓을 몇 시간 단위로 트렁크에 합친다. 그 속도를 지키는 건 평가자와 CI이고, 진척도는 git과 이슈에서 계산한다. 잎이 읽는 건 자기 티켓과 부모 이슈뿐이다.

각 단계는 같은 칸으로 적는다: **들어오는 것 · 하는 일 · 나가는 것 · 누가 · 막히면**. 블록을 갈아끼워도 이 칸이 맞으면 흐름은 이어진다.

## 진척도와 기록

진척도는 계산하고, 기록에는 계산으로 알 수 없는 "왜"만 남긴다. 잎이 읽는 곳은 자기 티켓과 부모 이슈 둘뿐이고, 형제 PR은 부모가 다시 계획할 때만 읽는다.

| 무엇 | 어디에 | 누가 쓰나 | 누가 읽나 |
| --- | --- | --- | --- |
| 끝났나 | 이슈 상태, PR 머지 여부 | 자동 | 모두 |
| 다음에 무엇을 할지 | 이슈 트리에서 계산 | 자동 | 4 잎 고르기 |
| 바뀐 약속 | 부모 이슈에 한 줄씩 덧붙임 | 그 약속을 바꾼 잎이 머지될 때 | 3 쪼개기 (다음 잎 티켓을 쓰는 AI) |
| 결정과 이유 | PR 본문 (템플릿) | 생성자 | 다시 계획하는 부모, 사람 |
| 막힌 이유 | 티켓 댓글 | 실패한 세션 | 같은 잎의 다음 시도 |

부모 이슈의 "바뀐 약속"은 덧붙이기만 한다. 고치지 않으니 여러 잎이 동시에 써도 부딪히지 않는다. "끝났음" 같은 줄은 어디에도 적지 않는다.

PR 템플릿:

```markdown
## 의도
- 티켓: #
- 부모 목표:

## 결정과 이유
- 다른 방법 대신 이걸 고른 까닭

## 바꾼 약속
- 없음 / 넓히는 변경: 무엇을 추가했나 (깨는 변경은 여기 말고 부모에 제안)
- (채워져 있으면 머지할 때 부모 이슈에 한 줄 덧붙인다)

## 재계획
- 하다가 계획을 바꿨다면 무엇을, 왜

## 다음 사람에게
- 알아야 할 함정
```

## 지키는 장치

사람이 diff를 보지 않으니 빠른 머지를 받치는 건 아래 세 가지뿐이다. 하나라도 빠지면 그냥 빨리 망가진다.

| 장치 | 언제 | 무엇을 보나 | 못 보는 것 |
| --- | --- | --- | --- |
| 평가자 | 잎 PR을 올리기 전 | 티켓의 끝 기준을 직접 돌려본다. 쓰기 권한이 없고, 증거가 없으면 기본이 FAIL이다. 생성자의 "됐다"는 믿지 않는다 | 티켓 자체가 틀린 것 |
| 계약 테스트 | CI 안에서, 매 PR | 부모가 정한 자식끼리의 약속. 형제가 만든 걸 깨뜨렸는지. 기존 계약 테스트를 고친 PR은 머지를 막고 부모로 보낸다 | 약속 자체가 틀린 것 |
| CI | 잎 PR이 머지 큐에 들어갈 때, 최신 트렁크에 얹어서 | 전체 테스트와 빌드 | 테스트가 없는 곳 |

생성자가 직접 돌리는 테스트는 판정으로 치지 않는다. 자기 숙제를 자기가 채점하는 것이기 때문이다. 세 장치가 모두 못 보는 건 "만들려는 것 자체가 틀렸다"이고, 그건 8 뿌리 다시 보기에서 사람만 잡는다.

### 계약 테스트는 누가 검사하나

계약 테스트가 엉성하면 위 장치가 모두 통과로 보이면서 무너진다. 그래서 노드를 만들 때 검사한다. 노드의 인수 테스트도 같은 검사를 받는다.

- **처음엔 빨강:** 자식을 만들기 전에 돌리면 반드시 실패해야 한다. 아무것도 없는데 통과하면 아무것도 검사하지 않는 테스트다(TDD의 빨간불 먼저). CI가 계산한다.
- **약속 대조:** 평가자가 부모 이슈의 약속마다 대응하는 테스트가 있는지 본다. 쓰기 권한 없이 대조만 한다.
- **반복되면 뮤테이션 테스트:** 구현을 일부러 망가뜨려 계약 테스트가 잡는지 본다(1978년부터 있던 방법). 비싸서 엉성한 계약 테스트 때문에 사고가 반복될 때만 켠다.

### 위험 경로

인증·권한·결제·데이터 삭제·마이그레이션처럼 되돌릴 수 없는 곳은 잎 단위에서도 사람이 확인한다. 플래그를 꺼도 이미 일어난 삭제나 결제는 되돌아오지 않기 때문이다.

1. 위험 경로는 `CLAUDE.md`의 목록에 적는다
2. 사실 계산이 잎 PR이 그 경로를 건드렸는지 센다. 보안 계산 검사도 같이 돈다
3. 걸리면 평가자가 바뀐 동작을 "이렇게 부르면 이렇게 된다" 시나리오로 쓴다
4. 사람이 승인해야 머지 큐에 들어간다. diff는 보지 않는다

비용은 위험 경로를 건드린 잎에서만 사람을 기다리는 것이다.

## 트렁크와 잎 고르기

브랜치는 트렁크 하나뿐이다. 트리는 이슈에만 있고, 어느 노드의 잎이든 몇 시간 안에 트렁크로 합친다. 노드에는 브랜치가 없으니 노드가 얼마나 오래 걸리든 상관없다.

- **트렁크는 dev:** 모든 개발과 머지 큐는 dev에서 돈다. main에는 직접 커밋하지 않고(급한 수정도 dev로), 사람이 써 보고 괜찮다고 한 시점으로만 fast-forward한다. 합치는 게 아니라 옮기는 것이라 충돌이 없다.
- **배포:** 주기는 없다. 큰 가지 하나가 닫힐 때마다 "써 볼 차례"라고 알리고, 올릴지는 사람이 정한다(8 뿌리 다시 보기).
- **고르는 순서:** 준비된 잎 중 지금 집중하는 노드와 트리에서 가장 가까운 것부터 고른다. 형제, 한 층 위 사촌, 그 위 순으로 한 층씩 멀어진다. 가까운 곳에 할 잎이 없을 때만 멀리 간다.
- **범위 다이얼:** 최대 몇 층까지 올라가도 되나. 0이면 한 노드 안에서만 고른다(집중, 순서대로). 끝까지 열면 트리 전체에서 고른다(병렬). 혼자면 자연히 좁게, 팀이면 넓게 돈다.
- **덜 된 기능은 숨긴다:** 연결하지 않거나 기능 플래그로 끈다. 부모가 닫힐 때 플래그 지우기 잎을 자동으로 만든다.

6 막힘과는 방향이 반대다. 막히면 위로 올라가서 다시 짜고, 노드가 커지면 아래로 한 층 더 쪼갠다.

### 넓게 돌 때 충돌 피하기

AI 이전에 쓰던 네 가지 방법에서 좋은 점만 가져왔다.

| 방법 | 어디서 왔나 | 언제 |
| --- | --- | --- |
| 머지 큐: PR마다 최신 트렁크에 얹어 테스트하고 하나씩 합친다. 직접 만든 순차 머지(잠금 + rebase + CI)로 하고, 조직의 공개 저장소면 GitHub 머지 큐를 쓴다 | [Not Rocket Science Rule](https://graphite.com/blog/bors-google-tap-merge-queue) (Rust, bors) | 항상 |
| 바뀔 이유 단위로 쪼개고, 범위가 겹치는 잎은 동시에 고르지 않는다 | [Parnas (1972)](https://www.cs.lafayette.edu/~gexia/cs301/resources/parnas.html), 콘웨이 법칙 | 넓게 돌 때 |
| 같은 충돌이 세 번 난 파일은 쪼갠다 | [언리얼 One File Per Actor](https://dev.epicgames.com/documentation/en-us/unreal-engine/one-file-per-actor-in-unreal-engine) | 반복될 때 |
| 합칠 수 없는 파일만 잠근다 | Perforce, Git LFS 잠금 | 바이너리 에셋 등 |

## 약속 바꾸기

잎은 약속을 넓힐 수만 있고, 깨는 변경은 제안만 한다. 잎이 계약 테스트를 고칠 수 있으면 자기 PR이 통과하도록 테스트를 느슨하게 만들 수 있기 때문이다.

| 변경 | 예 | 누가 정하나 | 계약 테스트 |
| --- | --- | --- | --- |
| 넓히는 변경 | 새 함수, 선택 필드 추가 | 잎이 혼자. 머지할 때 부모 이슈에 한 줄 | 새 테스트만 더한다 |
| 깨는 변경 | 형제가 쓰는 걸 바꾸거나 없앰, 약속대로는 구현이 안 됨 | 잎은 멈추고 제안한다. 그 노드의 재계획 AI가 정하고, 큰 가지 수준 약속이면 사람이 정한다 | 기존 테스트를 고치면 CI가 자동 머지를 막는다 |

깨는 변경은 되도록 병렬 변경(expand–contract)으로 바꾼다. 동시에 돌던 형제가 깨지지 않고, 아무도 기다리지 않는다.

1. 잎은 옛 방식을 두고 새 방식을 옆에 추가한다. 넓히는 변경이라 바로 머지된다
2. 부모가 형제들을 새 방식으로 옮기는 잎 티켓을 만든다
3. 다 옮기면 마지막 잎이 옛 방식을 지운다

## 기획 대화

1단계는 질문 몇 개에 답하고 끝나는 게 아니라, 원하는 걸 세우는 긴 대화다. Omagari를 기획한 방식 그대로다.

1. **말로 푼다.** 문서 형식을 신경 쓰지 않고 무엇을 만들고 싶은지만 계속 말한다
2. **셀프 그릴링.** AI가 스스로 최대 15라운드를 돈다. 질문마다 자기 답을 같이 쓰고, 정한 것끼리 모순되는지 보고, 사람이 정해야 하는 것만 묻는다. 판단이 서면 일찍 끝낸다
3. **이미 있는 걸 찾는다.** 공식 기능, 오픈소스, 연구를 훑어 대체할 수 있는 것은 빼고 빈자리만 남긴다
4. **기획 문서 하나에 반영한다.** 설계 문서가 아니라 의도를 다듬은 기록이다
5. **살이 붙으면 갈아엎는다.** 발견할 때마다 덧붙여서 무거워지면 기획만 남게 처음부터 다시 쓴다
6. **끝낼 때만 하네스 형식으로 뽑는다.** 성공 기준과 확인 방법, 위험 경로, 평가자 준비물(테스트 계정, 시드 데이터), 기술 스택과 큰 구조(선택지로 고르고 ADR로 남김), 안 할 것. "명세 점검"이 다 있는지 세고, 빠지면 기획 대화로 돌아간다. 내용이 맞는지는 8에서 사람이 본다. 이걸 담은 뿌리 이슈가 기획 문서를 가리킨다

기획 문서가 원본이고, 뿌리 이슈는 거기서 뽑은 것이다. 8에서 "아니다"가 나오면 이 대화로 돌아와 기획 문서부터 고친다.

## 뿌리 다시 보기

평가자는 검증하고, 사람은 확인한다. 평가자는 명세를 기준으로 보니 명세 자체가 틀린 건 못 잡는다. 그래서 8은 사람이 원하는 걸 끌어내는 단계다. 1의 그릴링이 만들기 전에 묻는다면, 8은 만든 걸 손에 쥐여주고 묻는다.

1. 큰 가지가 닫히면 평가자가 뿌리의 성공 기준을 처음부터 끝까지 돌려보고 한 장짜리 보고서를 쓴다.
   - 되는 것, 플래그로 꺼진 것
   - AI가 방향을 바꾼 곳 (PR의 재계획 칸, 깨는 변경 결정)
   - 평가자가 확신하지 못한 곳
   - 사람이 해볼 시나리오 3개
2. 사람은 보고서를 읽고 시나리오를 해본다. 부족하면 더 만들게 한다.
3. 답은 셋 중 하나다. 맞다 → main으로 올린다 · 아니다 → 뿌리를 고친다 · 이건 다르게 → 그 큰 가지를 재계획한다.

방향이 어긋나는 일은 대개 AI가 혼자 방향을 바꾼 곳에서 생긴다. 그래서 사람은 diff 대신 그곳만 본다.

같은 모델이 짜고 평가하는 실은 남는다. 쓰기 권한 없음, 기본 FAIL, 분리된 컨텍스트로 줄이고, 필요하면 평가자만 다른 모델을 쓴다.

이걸 하려면 1에서 성공 기준을 평가자가 돌려볼 수 있게 적어야 한다. "로그인이 잘 된다"가 아니라 "가입한 이메일로 로그인하면 대시보드가 뜬다"처럼.

## 재계획

재계획은 이미 있는 규칙들(6 막힘, 약속 바꾸기, 8 뿌리 다시 보기)이 모이는 한 지점이다. 노드의 "어떻게"는 AI가, "무엇을"은 사람이 바꾼다. 지휘관의 의도는 고정하고 방법은 현장이 바꾸는 임무형 지휘(Auftragstaktik)와 같다.

| 신호 | 어디서 다시 짜나 |
| --- | --- |
| 같은 잎이 세 번 막힘 | 그 잎의 부모 노드 |
| 잎의 깨는 변경 제안 | 그 약속을 정한 노드 (부딪힌 잎들의 공통 부모) |
| 8에서 "이건 다르게" | 그 큰 가지 |
| 8에서 "아니다" | 뿌리 |

1. 그 노드 아래 잎 고르기를 멈춘다. 돌고 있는 잎은 끝내고, 그 결과도 재료로 쓴다.
2. 노드 이슈, 자식 상태, 자식 PR의 결정과 재계획 칸, 막힌 이유를 읽는다. 형제 PR을 몰아 읽는 건 이때뿐이다.
3. 셋 중 하나를 한다.
   - 열린 자식만 다시 쪼갠다. 닫힌 자식의 코드는 되돌리지 않고, 꼭 빼야 하면 플래그를 끄거나 되돌리기 잎을 만든다.
   - 약속을 병렬 변경 잎들로 바꾼다.
   - 이 노드 목표 안에서 안 풀리면 한 층 위로 올린다.
4. 무엇을, 왜 바꿨는지 노드 이슈에 한 줄 남긴다. 8 보고서의 "AI가 방향을 바꾼 곳"이 된다.

같은 노드에서 재계획이 세 번 실패하면 한 층 위로 올린다.

**"무엇을"을 바꿨는지는 CI가 잡는다.** 노드의 목표는 인수 테스트로 적고, 재계획은 그 테스트를 고칠 수 없다. 고쳐야 하면 목표를 바꾸는 것이니 사람에게 간다.

**테스트로 못 잡는 건 바로 알린다.** 인수 테스트는 통과하는데 사용자에게 보이는 동작이 바뀌면(비밀번호 로그인 → 매직 링크), 사람에게 한 줄로 바로 알린다. 작업은 멈추지 않고, 사람이 보고 아니면 막는다. 이 빈틈은 없앨 수 없고, 빨리 보이게만 한다.

## 사람이 끼는 곳

사람은 방향과 의도만 정한다. diff도, 잎 티켓도 보지 않는다.

- 1 뿌리 명세: 기획 대화를 한다. 며칠에서 몇 주가 걸려도 된다. 사람 시간을 여기에 몰아 쓴다
- 2 큰 가지: 득실을 보고 안을 고른다
- 5 위험 경로: 잎이 위험 경로를 건드렸을 때 동작 시나리오를 보고 승인한다
- 6 막힘: 위로 올라가다 큰 가지까지 닿았을 때
- 8 뿌리 다시 보기: 큰 가지가 닫힐 때마다 평가자 보고서와 시나리오로 원하는 게 맞는지 확인한다. 괜찮으면 main으로 올린다
- 재계획: 목표를 바꿔야 할 때, 그리고 동작 바뀜 알림을 보고 아니다 싶을 때
- 9 빈틈: 하네스 수정안을 넣을지 고른다

## 아직 정하지 않은 것

- [x] 재계획 → 재계획 (어떻게는 AI, 무엇을은 사람)
- [x] 잎이 약속을 혼자 바꿔도 되는지 → 약속 바꾸기
- [x] 하루 안에 안 끝나는 노드는 어떻게 하는지 → 트렁크와 잎 고르기 (노드에 브랜치 없음)
- [x] 트렁크와 배포 → 트렁크는 dev, 사람이 써 본 시점만 main
- [x] 뿌리를 다시 볼 때 무엇을 보고 판단하는지 → 뿌리 다시 보기 (평가자는 검증, 사람은 확인)
- [x] 부모가 정한 약속이 처음부터 틀렸을 때 → 약속 바꾸기의 깨는 변경
- [x] 계약 테스트는 누가 검사하나 → 지키는 장치 (처음엔 빨강, 약속 대조)
- [ ] 작은 프로젝트 하나에 실제로 돌려보기

없앨 수 없는 것 (알고 쓴다):

- 실제로 돌려보기 전까지 이 조합은 머릿속 설계다
- 인수 테스트는 통과하지만 목표가 바뀐 재계획은 알림과 8로만 잡힌다
- 같은 모델이 짜고 평가하는 편향
- 잎마다 평가자, 머지 큐 CI, 재계획이 드는 비용
