# Kagami 가운데 설계

2026-11-04 · baekchan

사람이 흐름을 쥐고, 되돌리기 어려운 결정만 사람에게 올린다. 트리는 GitHub 이슈에 두고, 일은 Claude Code 대화에서 한다. 자율은 근거가 쌓인 단계만 하나씩 늘린다.

## 왜 바꿨나

0단계(T0~T12)는 "사람은 1, 2, 8단계에만 낀다"는 완전 자율을 목표로 나흘 만에 PR 20개를 만들었다. 장치는 스무 개 가까이 쌓였지만, 사람은 흐름을 쥐지 못했다. 배운 것은 세 가지다.

1. **재지 않은 건 지켜지지 않는다.** 성공 기준 다섯 개가 전부 장치가 도는지에 관한 것이었고, "사람이 각 결정을 알고 넘어간다"는 없었다
2. **경계선이 틀렸다.** "어떻게는 AI, 무엇을은 사람" 안에 되돌리기 어려운 구조 결정(상태를 댓글로 두기, `/다르게` 해석, 계속 도는 loop)이 섞였다. 기준은 "되돌리기 쉬운가"였어야 한다(블록 사전 원칙 5)
3. **진짜 일을 한 번도 안 했다.** 장치 대부분이 일어난 적 없는 문제를 미리 막는 것이었다(원칙 4 위반). 시험 저장소의 장난감 함수로만 돌렸다

복잡함은 하네스라서 생긴 게 아니라 자율성의 값이었다. 그래서 방향은 "가운데"로 간다. 새 방향이라기보다 블록 사전의 다이얼(L1부터, L4는 실적이 쌓였을 때만)로 돌아가는 것이다.

## 원칙

철학은 그대로다. AI는 증폭기고, 사람은 원하는 것과 책임을 가진다. 구멍은 누가 해도 생기고, 그걸 고치는 게 일이다.

1. **사람이 흐름을 쥔다.** 다음 일은 사람이 고른다. 흐름은 Claude Code 대화가 쥐고, GitHub는 트리(하위 이슈, blocked-by)와 기록, 진척도(Projects)를 담는다
2. **되돌리기 어려운 결정은 사람에게 올린다.** 나머지는 AI가 정하고 PR의 `Decided`에 남긴다
3. **사람이 읽는 글은 두 질문에 먼저 답한다.** 지금 트리의 어디냐, 이번에 뭘 만드냐. 쉽게 설명했는데도 안 읽고 넘기는 건 사람의 책임이다
4. **기록은 이슈에 남긴다.** 대화가 끝나면 결정도 사라지므로, 물은 것과 답, 바뀐 약속은 그 이슈에 두어 다음 세션이나 다른 사람이 이어받게 한다
5. **규칙은 저장소 문서에 둔다.** `AGENTS.md`에 적고 CC 스킬에만 넣지 않는다. 누가 어떤 에이전트를 쓰든 같은 문서를 읽게
6. **강제는 최소로.** 이미 있는 것(CC의 권한 확인, CI)을 쓴다. 막는 장치는 같은 문제가 3번 반복됐을 때만 더한다
7. **자율은 근거가 쌓인 단계만 늘린다.** "매번 그냥 승인한 단계"를 기록해 두고, 그게 쌓인 단계부터 맡긴다
8. **구조는 처음부터 여럿일 때와 같게.** 사람도 에이전트도 트리의 일꾼 하나다. 숫자만 1일 뿐이다

## 한 번 일하는 흐름

고른 일 하나를 세션 하나에서 끝낸다. 뿌리는 미리 `/kagami:plan`(기획 대화)로 세워져 있고 명세 점검을 통과했다고 본다.

1. **열기:** CC 세션을 열고 저장소를 알려 준다
2. **추천:** CC가 트리를 읽고 지금 할 수 있는 일 중 성격이 다른 것 2~3개를 이유와 함께 낸다. 예: 제일 빨리 끝나는 것, 다른 일을 제일 많이 풀어 주는 것, 사람 판단이 필요한 막힌 것. "뭘 하고 싶어?"를 먼저 묻지 않는다
3. **고르기:** 사람이 고른다. 셋 다 아니면 대화로 찾고, `off-recommendation`으로 기록한다. 고른 일은 고른 사람에게 할당된다(아래 "할당과 이어받기")
4. **계획 알림:** 배경 → 이번에 할 것을 짧게 보여 준다. 티켓대로면 멈추지 않고 진행한다. 티켓에서 벗어나거나 사람에게 올릴 결정이 끼면 선택지로 물어보고 기다린다
5. **구현:** `/kagami:build`로 테스트부터 쓴다. 명세에 없는 애매한 부분은 그 자리에서 묻는다
6. **평가:** 쓰기 권한 없는 평가자 에이전트가 끝 기준과 범위로 판정한다. FAIL이면 고치고 다시, 3번이면 멈추고 사람에게 알린다
7. **PR:** 제목은 Conventional Commits(`feat:`, `fix:` …), 본문 맨 위에 TL;DR, 그리고 `Closes #<잎 번호>`
8. **동의와 머지:** CI가 초록이면 TL;DR을 보여 주고, 사람이 대화에서 동의하면 CC가 squash로 머지한다. 잎 하나가 dev 커밋 하나가 되고, PR 제목이 그 커밋 메시지가 된다. `gh pr merge`는 자동 허용하지 않아서 CC의 권한 확인이 곧 동의가 된다
9. **기록하고 끝내기:** 물은 것과 답은 그 일의 이슈에, 바뀐 약속은 부모 이슈에, 새로 찾은 일은 새 이슈로 남기고 세션을 클리어한다

### 큰 가지 확인

잎이 다 닫힌 큰 가지는 사람이 써 보고 확인한다(원래의 8단계). 큰 가지 이슈는 확인이 끝날 때까지 열어 두고, 이슈에는 끝 기준과 써 볼 시나리오 3~5단계를 적어 둔다.

1. 평가자가 자동 끝 기준을 확인한다. FAIL이면 고칠 잎을 만든다
2. CC가 실행 방법과 시나리오를 안내한다
3. 사람이 써 보고 말로 답한다
4. CC가 답을 셋 중 하나로 나누고 한 줄로 되묻는다
   - **괜찮다:** 그 커밋에 릴리즈 태그 `v*`를 달고 GitHub Release를 만든다(설명은 그 가지 잎들의 PR 제목). 큰 가지를 닫는다
   - **고칠 게 있다:** 큰 가지 아래 새 잎을 만든다
   - **원한 게 달랐다:** 명세를 바꾸는 안을 `needs-decision`으로 올린다

첫 릴리즈는 `v1.0.0`이다. `v1.0.0` 전에는 태그 없이 닫는다: 확인이 "괜찮다"여도 태그와 GitHub Release 없이 큰 가지만 닫는다.

main 브랜치는 두지 않는다. dev 하나뿐이고, "사람이 써 본 시점"은 태그가 표시한다. 태그는 두 가지다: 릴리즈 `v*`, 보관 `archive/*`. 태그 push는 자동 허용하지 않아서 CC의 권한 확인이 곧 동의다. 버린 대안은 main 브랜치를 확인한 커밋으로 앞당기는 방식이었다. 브랜치가 하나 더 있어야 하고 hook으로 지켜야 한다.

## 역할은 일의 상태가 정한다

사람이나 에이전트에게 역할을 미리 나눠 주지 않는다. 고른 일의 상태가 그 세션의 역할을 정하고, 역할을 끝내면 세션도 끝난다.

| 고른 일의 상태 | 역할 | 쓰는 것 | 끝나면 남는 것 |
|---|---|---|---|
| 칸이 빠진 뿌리 | 기획 대화 | `/kagami:plan`, 명세 점검 | 기획 문서, 뿌리 이슈 |
| 자식이 없는 노드 | 쪼개기 | 트리에 맞춘 쪼개기(`/kagami:split`) | 자식 잎 이슈, 계약 테스트 |
| 준비된 잎 | 구현 | `/kagami:build` | PR과 TL;DR |
| 리뷰 없는 PR | 평가 | 쓰기 권한 없는 평가자 에이전트 | 판정(PR 댓글) |
| 잎이 다 닫힌 큰 가지 | 확인 | 평가자의 검증 + 사람의 시나리오 | 괜찮다 / 고칠 게 있다 / 원한 게 달랐다 |
| 막힌 일 | 다시 보기 | 이어가지 않고 새 세션 | "이래서 막혔다" 한 줄 |
| 사람의 답이 필요한 질문 | 답하기 | 사람 | 이슈에 질문과 답 |
| 머지 | 동의 | 사람 (CC 권한 확인) | dev 커밋 |

"부모"는 살아 있는 세션이 아니라 노드 이슈다. 부모 세션을 살려두면 맥락이 쌓이고 사람과 자식 사이의 중간자가 된다. 0단계에서 사람이 원본 대신 부모 세션의 요약만 본 게 그 문제였다.

## 사람이 읽는 글

사람이 읽는 글은 두 가지뿐이다. 둘 다 맨 위 두 줄이 "지금 어디서, 뭘 만드나"다. 사람은 diff를 읽지 않는다(블록 사전 원칙 1).

**계획 알림** (구현 전, 열 줄 안쪽)

```markdown
Where: <뿌리> › <큰 가지> › #<잎 번호> <이름>
Why: 왜 이 일인지 (2~3줄)
Scope: 이번에 할 것 (3줄 안)
Done when: 끝 기준
Decide: (있을 때만) 선택지 2~3개, 득실, 추천 하나
```

`Decide`가 없으면 알리기만 하고 진행한다. 있을 때만 멈춘다. 고르려면 읽어야 하니, 꼭 읽어야 할 때만 읽게 된다. 항목 이름은 영어, 내용은 한국어로 쓴다.

**PR TL;DR** (PR 본문 맨 위)

```markdown
Where: <뿌리> › <큰 가지> › #<잎 번호>
What: 한 것 (3줄 안)
Changed:
- new issues / plan changes / contract changes / risk paths touched / new dependencies
Decided: AI가 혼자 정한 것과 이유만
```

- **사실은 계산으로 채운다.** `Changed`는 스크립트가 센다(새 이슈, 바뀐 계약 테스트, 위험 경로, 의존성)
- **AI는 "왜"만 쓴다**
- **평가자는 TL;DR이 diff와 맞는지도 본다.** 빠뜨린 게 있으면 FAIL이다. 만든 쪽이 자기 일을 요약하는 자기 신고를 막기 위함이다

## 사람에게 올리는 결정

기준은 "되돌리기 쉬운가"다. 쉬우면 AI가 정하고 기록한다. 어려우면 선택지로 묻는다. 아래는 첫 목록이고, 실제로 "이건 내가 알았어야 했다" 싶은 사례가 나오면 더한다.

- **겉으로 드러나는 동작:** 사용자가 보거나 느끼는 것이 바뀐다 (예: 비밀번호 로그인 → 매직 링크)
- **부품 사이의 약속:** 계약 테스트, 데이터 형식, 상태를 어디에 둘지
- **권한과 보안:** 인증, 권한, 비밀값, 위험 경로
- **스택과 큰 구조:** 언어, 프레임워크, DB, 저장소 구조. ADR로 남긴다
- **범위의 변화:** 티켓에서 벗어나거나 "안 할 것"을 하게 될 때

물을 때는 선택지 2~3개에 득실을 "좋은 점 / 대가" 문장으로 붙이고 추천 하나를 고른다. MADR의 "Good, because / Bad, because"와 같은 형식이다.

### 틀 쏠림 다루기

선호는 선택지를 받는 과정에서 만들어진다(Lichtenstein & Slovic). 그래서 AI가 틀을 깔면 사람의 선택이 AI가 깔아 준 범위로 쏠린다. 위임은 후회를 줄여 주지만 책임을 흐린다(Anderson 2003, 2023 메타분석).

- **추천은 일부러 성격이 다르게** 낸다. 셋이 비슷하면 쏠림이 커진다
- **"셋 다 아님"을 기록한다.** 사람이 추천을 벗어난 곳이 AI의 틀이 놓친 곳이다
- **"전부 수락" 실험을 한다.** 추천만 따라 돌려서, "내가 원한 게 아닌데"가 처음 나오는 지점을 찾는다. 득실을 기록이 아니라 내 선호를 발견하는 도구로 쓰는 방법이다. 아래 "첫 실전 계획"의 1회차가 이것이다

### 첫 실전 계획

중간 크기의 진짜 프로젝트를 두 번 돌린다.

- **1회차 "전부 수락":** 추천은 늘 1번, Decide는 늘 CC 추천, 머지 동의는 늘 "ㅇㅇ", 사람이 직접 고치지 않는다. 큰 가지 확인만 진짜로 한다
- **2회차 "가운데":** 이 문서대로 사람이 고르고 묻고 동의한다

고정 규칙:

- 뿌리는 한 번 세워 두 회차가 같이 쓴다
- 저장소는 회차마다 하나씩, 둘이다
- 두 저장소 모두 같은 kagami 태그를 쓴다
- 1회차(전부 수락)의 큰 가지 확인에서 "괜찮다"가 아닌 첫 답에는 `**not-what-i-wanted**`를 단다(표시어만, 라벨 없음)

비교할 것:

- 처음 깨진 지점: `**not-what-i-wanted**`가 처음 달린 곳
- 원한 거냐: 끝난 결과가 원한 것인가
- 걸린 시간

## 세션 수명과 잎 크기

고른 일 하나 = 세션 하나다. 새 세션은 이전 대화를 몰라도 그 일의 이슈와 부모 이슈만 읽고 시작할 수 있어야 한다.

- **끝내기 전에 옮긴다:** 물은 것과 답 → 그 일의 이슈, 바뀐 약속 → 부모 이슈, 새로 찾은 일 → 새 이슈, 추천을 벗어났으면 그 사실. 그다음 클리어한다
- **spec-gap:** 티켓과 부모 이슈에 없는 정보가 필요했으면 `**spec-gap**`을 이슈에 남긴다. 쌓이면 쪼개기에서 무엇을 빠뜨리는지 보인다
- **막히면 이어가지 않는다:** `**blocked**`를 남기고 할당을 푼 뒤 새 세션에서 다시 한다. 풀 일이 있으면 새 이슈 + blocked-by
- **예외는 기획 대화다:** 며칠씩 가니 세션이 끊기는데, 기획 문서가 상태를 들고 있어서 괜찮다

**잎 크기는 사람이 읽는 글의 길이로 잰다.** 컨텍스트가 차는 것은 신호로 너무 늦다. 쉽게 설명이 안 되는 잎은 사람이 확인하기에도 너무 큰 잎이다.

| 언제 | 신호 | 할 일 |
|---|---|---|
| 시작 전 | 계획의 `Scope`가 3줄을 넘는다 | 시작하기 전에 쪼개자고 제안 |
| 하는 중 | 범위 밖 파일이 필요하거나 바뀐 줄 수가 커진다(`git diff --stat`) | 멈추고 알린다 |
| 끝난 뒤 | TL;DR의 `What`이 3줄을 넘거나 FAIL이 반복됐다 | 다음엔 더 작게 쪼개라고 기록 |

쪼개야 할 때는 그 세션이 잎을 노드로 바꾸고 자식 잎 이슈를 만든 뒤 끝난다. 자식은 다음 세션에서 하나씩 고른다.

### 할당과 이어받기

처음부터 여럿이 써도 같은 일을 두 번 잡지 않게, GitHub assignee로 "누가 하는 중"을 표시한다.

- **잡기:** 고른 일은 잎만이 아니라 모두(쪼개기, 기획 대화 포함) 고른 사람에게 할당한다. CC는 할당 직전에 이슈를 다시 읽고, 그사이 누가 가져갔으면 다시 추천한다. 할당된 일은 "준비됨"에서 빠진다
- **풀기:** PR이 머지되면 이슈가 닫힌다. PR이 머지 없이 닫히거나, `blocked`를 남기거나, 할당된 채 3일 동안 활동(잎 브랜치 푸시, PR, 이슈 댓글)이 없으면 푼다. 오래된 할당은 세션을 열 때 CC가 훑어 푼다. 풀 때마다 `**released**`를 남긴다
- **이어받기:** 고른 잎에 예전 브랜치가 남아 있으면 CC가 diff와 이슈 기록을 보여 주고, 이어갈지 처음부터 할지 사람이 고른다. 다른 사람의 작업을 이어가면 `Co-authored-by:`로 출처를 남긴다. Rust·Kubernetes의 "take over" 관행과 같다

## 남는 장치와 kagami 전환

사람이 대화 안에 있으니 "사람이 단 승인인가"를 가를 일이 없다. 그래서 봇 계정과 /승인 댓글은 필요 없다. CC는 내 계정으로 이슈와 PR을 만든다.

| 장치 | 하는 일 | 어디서 왔나 |
|---|---|---|
| CC 권한 확인 | `gh pr merge`를 자동 허용하지 않아서, 머지 전에 사람이 동의한다 | Claude Code 기본 기능 |
| CI 가드 | 기존 계약 테스트 수정 감지, 래칫(한 번 초록이면 계속 초록). PR에 체크로 뜬다 | kagami T7 (승인 대기는 뺀다) |
| 명세 점검 | 뿌리의 칸이 다 있는지 센다 | kagami T12 |
| 평가자 에이전트 | 쓰기 권한 없이 끝 기준, 범위, TL;DR을 판정 | cwc-long-running-agents |
| 계약 테스트 | `contracts/<노드#>/`, 처음엔 빨강, 잎은 넓히기만 | kagami T5 |

**kagami 전환:** CC가 코드를 읽고 전환 잎 목록을 안 2~3개로 낸다. 남길 것, 고칠 것, 아카이브할 것, 지울 것도 파일별 근거와 함께 그 안에 넣고, 사람이 고른다. 다만 "있으니까 쓴다"를 조심한다. 자동화는 그럴 근거가 쌓인 단계가 생겼을 때만 다시 쓴다(원칙 7).

## 방법론 지도

새로 만든 것은 거의 없다. 검증된 방법들을 트리와 사람의 흐름으로 엮었다.

| 방법론 | 핵심 | 여기서 쓰는 곳 |
|---|---|---|
| [선호 구성](https://www.abebooks.fr/9780521834285/Construction-Preference-Lichtenstein-Sarah-Editor-0521834287/plp) (Lichtenstein & Slovic) | 선호는 물어보는 과정에서 만들어지고, 묻는 방식에 따라 뒤집힌다 | 기획 대화, 추천을 성격 다르게, 틀 쏠림 기록 |
| [결정 회피](https://research.tilburguniversity.edu/en/publications/the-psychology-of-doing-nothing-forms-of-decision-avoidance-resul/) (Anderson 2003), [2023 메타분석](https://pmc.ncbi.nlm.nih.gov/articles/PMC10575496) | 위임은 책임을 피하게 해 후회를 줄인다 | "전부 수락" 실험, 안 읽고 넘기는 건 사람의 책임 |
| ADR (Nygard), [MADR](https://ozimmer.ch/practices/2022/11/22/MADRTemplatePrimer.html) | 결정마다 선택지와 "Good, because / Bad, because"를 남긴다 | 사람에게 묻는 형식, PR의 `Decided`, 스택 ADR |
| 블록 사전 다이얼 (L1~L4) | 사람이 얼마나 볼지. L4는 실적이 쌓였을 때만 | 자율은 근거가 쌓인 단계만 |
| Boehm의 검증과 확인 | "명세대로 만들었나"와 "원한 게 맞나"는 다르다 | 평가자는 검증, 사람은 큰 가지마다 확인 |
| WBS, HTN, ADaPT | 큰 일을 트리로, 막힐 때만 더 쪼개기 | 이슈 트리, 잎이 크면 쪼개기 |
| [Parnas (1972)](https://www.cs.lafayette.edu/~gexia/cs301/resources/parnas.html) | "바뀔 이유" 단위로 나눠야 서로 덜 부딪힌다 | 잎의 범위 |
| 칸반 당기기 | 할 사람이 생길 때만 일을 꺼낸다 | 필요할 때만 쪼개기 |
| [Beads](https://www.morphllm.com/beads-agent-memory) | 의존성 그래프에서 지금 할 수 있는 일만 뽑는다 | 다음 일 추천, `discovered` |
| DORA, 트렁크 기반 개발, 기능 플래그 | 브랜치는 짧게, 덜 된 기능은 숨겨서 매일 합친다 | dev 트렁크 하나, 사람이 써 본 시점은 태그 |
| [Not Rocket Science Rule](https://graphite.com/blog/bors-google-tap-merge-queue) | 최신 트렁크에 얹어 테스트한 것만 들인다 | CI 초록일 때만 머지 |
| 계약 테스트, 병렬 변경(expand–contract) | 옛 방식을 두고 새 방식을 옆에, 다 옮기고 지운다 | 약속 바꾸기, 래칫 |
| TDD 빨간불 먼저 | 테스트가 진짜 뭔가를 검사하는지 먼저 실패로 확인 | 처음엔 빨강 |
| 임무형 지휘 (Auftragstaktik) | 의도는 위가, 방법은 현장이 | **대체됨.** "어떻게/무엇을" 경계가 되돌리기 어려운 결정을 놓쳐서 "되돌리기 쉬운가"로 바꿈 |

## 기록의 모양

기록은 모두 이슈 댓글이고, 첫 줄이 굵은 영어 표시어로 시작한다. 본문은 한국어다. 표시어마다 같은 이름의 라벨을 붙여 보드에서 걸러 볼 수 있게 한다: `needs-decision`, `split`, `contract-change`, `blocked`, `off-recommendation`, `spec-gap`, `discovered`. `released`와 `not-what-i-wanted`는 표시어만 있고 라벨은 없다. `needs-decision`만 상태 라벨이다: 세션을 열 때 CC가 이 라벨이 붙은 이슈의 댓글을 읽고, 답이 있으면 사람에게 한 줄로 확인한 뒤 `**answer**`를 남기고 라벨을 뗀다. 답이 없으면 다시 묻는다. 그래서 답을 세션에서 하든 GitHub에서 하든 같이 정리된다. "준비됨"은 트리에서 계산하니 라벨로 두지 않는다.

| 표시어 | 무엇 | 어디에 | 예시 |
|---|---|---|---|
| `needs-decision` | 사람에게 물은 것과 답 | 그 일의 이슈 | **needs-decision** 빈 이름이면 무엇을 내나? ① "hi, " ② 에러 ③ "hi, 손님" → **answer** ③ (사람). 이유: 빈 이름은 손님으로 본다 |
| `split` | 쪼개기 결정 | 노드 이슈 | **split** 안 ②를 고름 (사람). ① 화면부터: 좋은 점 빨리 보인다 / 대가 API를 두 번 고침. ② API부터: 좋은 점 약속이 먼저 선다 / 대가 늦게 보인다. 자식 #40 #41 #42, 약속 `contracts/12/` |
| `contract-change` | 바뀐 약속 | 부모 노드 이슈 | **contract-change** #41이 `login()`에 선택 인자 `rememberMe`를 더함 (넓히기). PR #48 |
| `blocked` | 막힘. 풀 일이 있으면 새 이슈 + blocked-by | 그 일의 이슈 | **blocked** bcrypt 네이티브 빌드가 실패. 해본 것: 재설치, node 22. 다음엔: 순수 JS 구현으로 교체 → #52 (blocked-by) |
| `off-recommendation` | 추천 밖 선택 | 고른 일의 이슈 | **off-recommendation** 추천은 #21, #24, #27이었고 #30을 골랐다. 이유: 로그인보다 메모 저장이 먼저 궁금했다 |
| `spec-gap` | 티켓에 없던 것 | 그 일의 이슈 | **spec-gap** 세션 만료 시간. 부모 #12의 댓글에서 찾음. 다음 쪼개기 때 잎에 넣기 |
| `discovered` | 새로 찾은 일 | 새 이슈(알맞은 부모 아래) + 그 일의 이슈에 댓글 | **discovered** #55 비밀번호 재설정 메일. 찾은 곳: 로그인 실패 화면 |
| `released` (라벨 없음) | 할당을 푼 이유 | 그 일의 이슈 | **released** @baekchan. 이유: 3일 활동 없음 |
| `not-what-i-wanted` (라벨 없음) | 전부 수락 회차에서 "괜찮다"가 아닌 첫 확인 답 | 큰 가지 이슈 | **not-what-i-wanted** 메모 목록이 날짜순이 아니다. 고칠 게 있다 → #63 |
