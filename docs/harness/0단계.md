# 0단계: 하네스 만들기

이 탭은 새 세션이 이 기획 대화 없이 바로 만들기를 시작하기 위한 인수인계다. 무엇을 만드는지는 "전체 흐름" 탭, 무엇으로 만드는지는 "블록 목록" 탭, 어떤 순서로 만드는지는 이 탭을 본다. 원칙과 브릭의 출처는 [⛩️ harness is all you need](https://app.notion.com/p/4006ecddfa1c8185b979ffcf8dc2d5ac)다.

새 세션에 붙일 첫 메시지:

```txt
처음부터 끝까지 읽고 시작해줘: docs/harness/ 폴더의 세 파일
(하네스 전체 흐름.md, 블록 목록.md, 0단계.md)
이 트리 하네스를 TypeScript로 만드는 프로젝트야.
지금은 0단계고, "0단계 티켓 목록"의 T0부터 한 번에 하나씩 해.
설계를 바꿔야 할 것 같으면 구현하지 말고 먼저 나한테 물어봐.
```

## 이 하네스의 명세 점검

기획 대화 6번을 이 하네스 자신에 적용한 것이다. 이걸로 기획을 닫는다.

**성공 기준** (평가자가 돌려볼 수 있게)

- 시험 저장소에서 "메모 앱 로그인" 뿌리로 루프를 돌리면, 큰 가지 하나가 사람이 네 번 이하로 끼고 닫힌다
- 잎마다 평가자 판정이 남고, 평가자 세션에는 Write/Edit 권한이 없다
- 계약 테스트를 고친 PR은 머지되지 않는다 (일부러 그런 PR을 만들어 확인)
- 같은 잎이 세 번 막히면 재계획 신호가 뜬다 (일부러 못 푸는 잎을 넣어 확인)
- 정지 파일을 만들면 다음 잎을 시작하지 않는다

**위험 경로**: main을 옮기는 스크립트, 권한과 hook 설정(`.claude/settings.json`), CI 워크플로(`.github/workflows/`)

**평가자 준비물**: 시험용 GitHub 저장소 하나, 메모 앱 뼈대, 테스트 계정

**스택** (ADR-001)

- 트리 스크립트: TypeScript (Node). 이유: Claude Code의 mods와 플러그인이 TypeScript라 Omagari 어댑터, Kagami로 이어붙이기 쉽다. 버린 대안: Python(더 빠르지만 나중에 다시 짜야 할 수 있음)
- 세션 띄우기: `claude -p` (헤드리스 모드), 역할은 `.claude/agents/*.md`
- GitHub 다루기: `gh` CLI와 GitHub API (하위 이슈, blocked-by)
- CI: GitHub Actions

**안 할 것**: 일꾼 여러 개(숫자만 1로 두고 구조는 여럿일 때와 같게), Kagami, 묶음·영향 테스트, 뮤테이션 테스트, GitHub 머지 큐, UI, Notion 옮기기

## 0단계를 어떻게 돌리나

하네스가 아직 없으니 블록 사전 부록 B의 가벼운 티켓 루프로 만든다. 컴파일러 부트스트래핑처럼, 첫 버전은 다른 방식으로 만들고 그다음부터 자기 자신으로 돌린다.

1. **세팅:** 블록 사전 부록 C의 "프로젝트 시작할 때" 10단계를 그대로 한다. 여기에 dev 브랜치를 더한다
2. **티켓 하나 = 세션 하나:** 티켓마다 새 Claude Code 세션을 열고, 끝나면 닫는다. 컨텍스트가 오염되지 않게
3. **구현:** `/implement`로 테스트부터 쓴다
4. **평가:** `.claude/agents/evaluator.md`(Write/Edit 없음)에 부록 C의 평가자 프롬프트를 넣어 쓴다. NEEDS\_WORK면 고치고 다시 평가, 3번까지
5. **머지:** PASS에 CI까지 통과하면 사람이 머지한다. 하네스를 지킬 장치가 아직 없으니 0단계만은 자동 머지 대신 PR까지다
6. **위험 경로:** T7, T10, T11처럼 위험 경로를 만드는 티켓은 동작 시나리오를 보고 승인한다

cwc-long-running-agents에서 가져오는 파일은 Apache-2.0이라 출처를 표기한다.

## 0단계 티켓 목록

출발은 끝까지 관통하는 엇은 조각(T1)이다. 그다음부터는 그 조각을 두껍게 만든다. 일꾼 수는 처음부터 파라미터로 두고 기본값만 1이다.

| 티켓 | 하는 일 | 끝났다는 기준 |
| --- | --- | --- |
| T0 뼈대 | TypeScript 프로젝트, 테스트 도구, `CLAUDE.md`, CI(타입체크·린트·테스트), dev 브랜치 | CI가 초록 |
| T1 관통 조각 | 열린 잎 하나를 골라 worktree → `claude -p` 구현 세션 → PR → 평가자 세션(쓰기 권한 없음) → PASS면 dev에 rebase, CI, 머지 → 이슈 닫힘. 고르기와 실패 처리는 최소로 | 시험 저장소에서 더미 잎 하나가 끝까지 간다 |
| T2 이슈 구조 | 노드·잎 이슈 템플릿, 하위 이슈와 blocked-by 읽기, 상태 라벨 | 트리를 읽어 JSON으로 내놓는다 |
| T3 잎 고르기 | 열림 · 기다림 끝 · 담당 없음 · 잠금 아님, 트리 거리순, 범위 다이얼, 담당 판정은 claim 댓글, assignee는 표시용 | 단위 테스트로 고르는 순서 확인 |
| T4 루프 세 겹 | FAIL 3번 → 막힘(새 세션), 막힘 3번 → 재계획 신호, 머지 실패도 FAIL로 셈, T3의 pick.ts를 leaf.ts와 CLI에 연결, 순차 머지에 잠금. 정한 것: 평가자 판정은 PR 댓글로 남기고 FAIL 횟수는 메모리로 센다 · 막힘 횟수는 stuck-N 라벨, 막힌 이유는 티켓 댓글 · 막힘과 끊긴 시도(claim 만료)는 같은 길로 "claim 놓기 + 막힘 1 + 막힘 이유 댓글"로 끝나고, 다시 시도는 다음 고르기에서 새 브랜치·새 세션으로 · 재계획 신호는 부모 노드에 replan 라벨 + 그 잎의 막힘 1\~3 이유를 모은 댓글. replan은 잎 고르기만 막고 돌고 있는 잎은 끝까지 두며, 떼는 건 T6 · 잠금은 따로 두지 않고 dev의 fast-forward가 잠금이다: 잎 브랜치를 최신 dev에 rebase·push하고 CI가 통과하면 force 없이 dev를 그 커밋으로 옮기고, 그 사이 dev가 움직여 거절되면 rebase부터 다시 하며 이것도 FAIL로 센다 | 일부러 못 푸는 잎으로 신호가 뜬다, 루프가 pick.ts로 잎을 고른다 |
| T5 쪼개기 | 쪼개기 신호(준비된 잎 < 일꾼 수), 쪼개기 세션(부모 이슈만 읽고 잎 티켓과 계약·인수 테스트), 처음엔 빨강, 평가자의 약속 대조. 정한 것: 댓글 읽는 곳 전부 --paginate · 클론 하나에 프로세스 하나(이미 쓰는 클론이면 시작 거부) · 계약·인수 테스트는 대상 저장소의 contracts/<노드 번호>/에 두고(`*.contract.*`, `*.accept.*`, 기본 테스트 글롭에 안 잡힌다) 노드와는 그 번호로 잇는다 · 처음엔 빨강은 하네스 스크립트가 PR 전에 계산하고 결과는 PR 댓글로 남긴다 · 파일 단위가 아니라 테스트 하나하나가 빨강이어야 통과 · 빨강의 이유가 "구현 안 됨"이어야 한다. 불러오기 실패나 문법 에러로 인한 빨강은 통과 아님 → 쪼개기가 약속(인터페이스)을 먼저 스텁으로 만든다(모양만 있고 "not implemented"를 던짐) · 노드가 이미 잎 조건을 만족하면 쪼개기 세션이 "그대로 잎"이라고 답하고 스크립트가 그 노드를 잎으로 바꾼다 · 쪼개기 결과(잎 티켓 JSON)는 contracts/<N>/leaves.json으로 같이 머지한다. dev에 contracts/<N>/이 있는데 노드에 자식이 없으면 다시 쪼개지 않고 leaves.json으로 이슈 만들기만 이어서 한다(머지와 이슈 만들기 사이에 죽었을 때 대비) · 역할 파일은 새로 만들지 않는다. 프롬프트는 하네스 저장소의 prompts/*.md(구현자 포함)로 빼서 읽고, 권한(allowedTools, 쓰기 여부)은 코드의 CLI 플래그로 건다 · 쪼개기 신호는 runLeaves 안에서 가장 가까운 안 쪼갠 노드 하나를 claim하고 쪼갠다 | 노드 하나가 잎으로 쪼개지고 테스트가 먼저 빨강이다 |
| T6 재계획 | 잠금, 재계획 세션(셋 중 하나), 노드 이슈에 한 줄, 인수 테스트 수정 감지, 동작 바뀜 알림. 정한 것: claim 하트비트(만료는 마지막 갱신 기준, 위험도 중간) · 재계획하면 막힌 잎은 닫거나 고쳐 쓰고 막힘 횟수는 0부터 · 라벨은 필요할 때 생성 · 모든 claude -p 세션(구현자·평가자·쪼개기·재계획)은 한 곳(session)에서 인증 없는 환경으로 띄운다(T7에서 당겨 옴) · 재계획 세션 권한은 쪼개기 세션과 같다. 남은 일: 재계획 노드 고르기는 트리 순서이고 범위 다이얼을 안 본다(일꾼이 여럿이고 replan 노드가 여럿일 때 거리순으로) · 재계획 세션이 읽는 자식 PR은 최근 200개까지 · 재계획을 반영하다 죽으면 replan이 남아 다시 짜고 반쯤 만든 잎이 남는다 · 동작 바뀜은 재계획 세션이 스스로 적는다(자기 채점에 가깝다. 평가자가 판정하게 바꿀지) · 노드 이슈 댓글은 하네스 계정이 사람 계정과 같으면 GitHub 알림이 안 간다 · up으로 부모에 올리면 올린 노드 아래 막힌 잎(stuck-3)이 남는데, 부모 재계획은 직속 자식만 읽고 검사한다. 부모가 그 노드를 닫아도 닫힌 노드 아래 열린 잎은 고르기에 다시 잡힌다 · claim 만료 판정의 기준 시각은 GitHub updatedAt이지만 cutoff는 로컬 시계라, 기계 시계가 ttl의 2/3 넘게 어긋나면 살아 있는 claim을 만료로 본다 · 재계획이 테스트를 새로 쓰지 않으면 처음엔 빨강이 "새 테스트 없음"으로 통과한다(고쳐 쓴 잎이 이미 초록인 테스트를 가리키면 일 없이 닫힐 수 있고, 지금은 약속 대조만 거른다) · 인수 테스트 수정 감지는 contracts/<그 노드>/만 본다(다른 노드는 T7 CI) · 세션마다 만든 빈 GH_CONFIG_DIR 임시 폴더를 지우지 않는다 | 재계획 신호에서 노드가 다시 쪼개진다 |
| T7 지키는 CI | 계약 테스트 수정 감지, 사실 계산, 위험 경로 대기(GitHub 댓글 /승인), 보안 계산 검사. 정한 것: dev에 보호를 걸 땐 하네스 계정을 우회 목록에(push HEAD:dev 방식이라) · 계약·인수 테스트 래칫: 한 번 초록이 된 테스트는 이후 모든 PR에서 초록이어야 한다. 아직 빨강인 건 봐준다. 통과 목록은 잎이 아니라 하네스가 기록한다(노드가 닫힐 때까지 기다리면 그 사이 형제가 깨뜨려도 못 잡는다) · ~~세션 환경에서 GitHub·git 인증 제거~~ 완료(T6, SSH_AUTH_SOCK 삭제·GIT_SSH_COMMAND=false·GIT_TERMINAL_PROMPT=0도 더함)(GH_TOKEN·GITHUB_TOKEN 삭제, GH_CONFIG_DIR 빈 폴더, GIT_CONFIG_COUNT로 credential.helper 비움). push와 이슈 쓰기는 하네스 스크립트만. node -e 같은 우회를 열쇠 단계에서 막기 위함 · 위험 경로에 prompts/와 세션 권한 플래그가 있는 곳 추가(어떻게 묶을지는 T7에서 정함). T7에서 정한 것: 판정은 하네스의 순차 머지(src/guard.ts merge(): rebase 뒤, push HEAD:dev 전)에서만 하고 결과(통과·막힘·대기와 이유)는 PR 댓글로. 무료 개인 비공개 저장소라 브랜치 보호·룰셋은 403. 나중에 공개 저장소로 돌리면 룰셋으로 "dev push는 하네스 계정만"을 건다. 판정은 계속 하네스에서만 하고 룰셋은 문만 잠그는 용도 · /승인은 대기 댓글 뒤에 하네스 계정이 아닌 사람 계정(user.type User, 협업자 이상)이 단 것만 센다. PR 워크플로가 bot으로 단 /승인은 세지 않는다. 하네스 전용 계정(GitHub App 또는 머신 유저)이 있어야 승인할 수 있다 · 래칫의 통과 목록은 저장하지 않고 머지 때마다 dev에서 계산한다(dev에서 초록 → HEAD에서 빨강이거나 사라짐이면 FAIL). 예외는 재계획의 병렬 변경(expand)이 자기 노드의 옛 계약 테스트를 고치거나 지울 때뿐 · 기존 계약·인수 테스트를 고친 잎은 고쳐 다시 하지 않고 막힘 1 + 그 계약의 노드(contracts/<N>)에 replan. 쪼개기·재계획 PR이면 FAIL로 다시 짠다 · 위험 경로·지운 테스트·보안 지적은 같은 길로 CI 뒤 /승인 대기. 새 의존성은 세서 댓글에만 · 보안 계산 검사는 하네스의 Biome --only=security로 바뀐 코드 파일 전체 · 세션 권한 플래그와 인증 제거는 src/session.ts 한 곳으로 모았다. 위험 경로는 prompts/, src/session.ts, src/guard.ts. 계약 테스트를 돌리는 node --test(처음엔 빨강·래칫)도 인증 없는 환경. 남은 일: 하네스 전용 계정은 사람이 만든다. 그 전까지 위험 경로 PR은 승인을 못 받고, /승인의 실제 확인도 그 뒤 시험 저장소에서(App 토큰이면 gh api user가 안 되니 계정을 인자로) · 병렬 변경의 마지막 잎(옛 방식 지우기)은 옛 계약 테스트를 못 지워 막히고 재계획으로 간다. 재계획(expand)이 지우게 prompts/replan.md에 적을지 · 래칫은 보호 밖에서 dev에 들어온 빨강을 "아직 빨강"으로 봐준다 · dev·잎 worktree에 의존성을 설치하지 않아, 의존성이 있는 대상 저장소에서는 dev 쪽 테스트가 불러오기 실패로 빨강이라 래칫이 아무것도 안 지킨다 · 래칫은 머지마다 contracts/ 전체를 dev와 HEAD에서 두 번 돈다 · 위험 경로는 앞부분 일치만(글롭 없음), 말로 적은 줄은 계산 못 한다 · 대기 중엔 일꾼 하나가 claim을 쥐고 기다린다. 사람이 PR을 닫으면 막힘 1로 센다 · 계약을 정한 노드가 닫혀 있으면 replan을 달아도 재계획하지 않는다 · 대상 저장소의 biome.json이 하네스 Biome과 안 맞으면 보안 검사를 못 돌려 대기로 간다 · 래칫은 잎 코드와 같은 프로세스에서 테스트를 돌려서, 잎 코드가 assert 같은 공유 모듈을 바꾸면 결과를 속일 수 있다(아직 안 일어남, 일어나면 escapes) | 계약 테스트를 고친 PR이 막힌다 |
| T8 부모 닫기와 8 | 자식이 다 닫히면 부모 닫기, 플래그 지우기 잎, 써 볼 차례 알림, 8 보고서 세션, 댓글 /맞다 /아니다 /다르게. 정한 것: 노드는 자식이 다 닫히고 인수 테스트가 초록일 때만 닫힌다. 자식은 다 닫혔는데 인수 테스트가 빨강이면 그 노드에 재계획 신호 | 큰 가지가 닫히면 보고서 이슈가 생긴다 |
| T9 템플릿 | PR 템플릿(바꾼 약속은 부모 이슈에 한 줄 덧붙임), 8 보고서, escapes, `escape` 명령 | 머지된 PR의 바꾼 약속이 부모 이슈에 보인다 |
| T10 정지와 방향 수정 | 정지 파일, 방향 수정 파일(cwc에서 가져옴), `stop`, `steer` 명령 | 정지 파일을 만들면 다음 잎을 시작하지 않는다 |
| T11 dev에서 main으로 | /맞다 뒤 fast-forward 스크립트, main 직접 커밋을 막는 hook | main은 fast-forward로만 움직인다 |
| T12 기획 대화 | 기획 대화 스킬(SKILL.md), 명세 점검 스크립트 | 빠진 항목이 있으면 명세 점검이 알려준다 |
